---
title: 压缩包口令破解的优先级
---

> **最短路径**：一小时后能不能出结果，在动手前就能算出来。
>
> 1. `7z l -slt <归档>` 看 `Method` —— 带 `AES` 是 A 级慢哈希，不带是 S 级 ZipCrypto，**速度差 44 万倍**，不先判这个后面全是瞎猜
> 2. `hashcat -b -m <模式>` 实测本机速度，乘上你愿意花的时间 = 可覆盖空间
> 3. **可覆盖空间小于候选量级，就直接判「不做硬破」** —— 止损也是一种结论
>
> 下面所有速度数字都来自 hashcat 7.1.2 + RTX 4070 Ti 的实机 `hashcat -b` 与批量跑测（2026-10 记录）。换硬件请按 §2 重新测，可覆盖空间是按你的卡算的。

## 适用范围

- 用于**自己遗忘口令的归档**、CTF / 靶场素材、以及明确授权的测试文件。
- 本文只讲「怎么排优先级、怎么止损」，不讲怎么获取别人的加密文件。
- 面向单机 GPU 场景。集群、FPGA、云上租卡是另一套经济账，不在这里。

## 五条核心原则

1. **先定算法，再谈口令强度。** 同样的 `.zip` 后缀可能是 ZipCrypto（3.9 GH/s），也可能是 WinZip AES（8.9 MH/s）——**速度差 44 万倍**。不判定算法就排优先级，等于瞎猜。
2. **一切以「实测速度 × 预算 = 可覆盖空间」为准。** 所有数字来自本机 `hashcat -b`，不用「感觉很快 / 很慢」。
3. **慢格式上，字典永远优先于掩码。** 1 小时在 RAR5 上能跑 4.3 亿条**字典**，但只能跑 8 位纯数字**掩码**。掩码是最后手段，不是首选。
4. **每阶段都要过验证闸门 + 口令横传。** 一个包的口令立刻拿去试其他包；任何「破解成功」都要验证明文可读性（见 §9，踩坑实录见 [实战复盘](./hashcat实战复盘.md)）。
5. **超过预算就停。** 停止不是失败，是止损；把结论写清楚比硬跑 20 小时有价值。

## 第一步：判定算法级别

这一步免费，且决定了后面所有事。

```bash
7z l -slt target.zip | grep -i method
```

- `Method` 里出现 `AES-256` 之类 → WinZip AES，hashcat 模式 `13600`，A 级
- 只有 `Deflate` / `Store`（而归档又确实需要密码）→ ZipCrypto，模式 `17200` / `17210`，S 级

7z 和 rar 同理，先看 `Method` 和版本头。**判错一级，预算表就全错。**

::: warning `hashcat -b` 的 11600 数字会骗人
它对 11600 默认显示 **1049 kH/s**，那是拿内置样例（`NumCyclesPower=14`）测的。真实归档默认是 **19**，也就是 **32 倍**工作量 → **32.8 kH/s**。直接信 `-b` 会让你把预算高估 32 倍。
:::

### 7-Zip 的速度不是常数

7-Zip 的 KDF 是**一条连续的 SHA-256 流**：把 `口令(UTF-16) + 8 字节计数器` 重复 2¹⁹ 次喂进去，所以总哈希字节数 ∝ 2¹⁹×(8+2L)。拟合出：

```text
7z 速度(H/s) ≈ 7.3×10⁵ / (8 + 2L)      L = 口令长度（UTF-16 码元数，ASCII 与汉字都算 1）
```

| 口令长度 | 实测速度 |
| ---: | ---: |
| 6 字符 | 34.1 kH/s |
| 8 字符 | 29.7 kH/s |
| 10 字符 | 26.1 kH/s |
| 12 字符 | 24.0 kH/s |
| 16 字符 | 19.2 kH/s |
| 20 字符 | 16.5 kH/s |

**推论**：报 7z 速度必须带口令长度；长口令掩码天然更贵，`--increment` 要**从短到长**跑，先把便宜的短长度扫完。

### 已经排除的「更快路子」

这些都是实测或查源码排除掉的，不必再试：

| 想法 | 结论 |
| --- | --- |
| 多开 hashcat 实例并行 | ❌ GPU 已 100% 占满（实测 100% / 2745 MHz / 79 °C / 245 W），无收益 |
| 跳过 LZMA2 解压 | ❌ 只差 6%（31.1 kH/s vs 33.0 kH/s）。KDF 是大头 |
| 用截断版哈希（type 0x80，padding attack） | ❌ **hashcat 7.1.2 已移除**：`module_11600.c` 明确拒绝 `data_type == 0x80` |
| `-O` 优化内核 | ✅ 有效，约 **+10%**（26.1 → 28.7 kH/s），代价是口令 ≤ 20 字节 |
| 手调 `-n/-u` | ❌ 该模式报 `Invalid kernel-loops specified`，交给 `-w 3/4` 自动调优 |
| 装 CUDA 后端替换 OpenCL | ⚠️ 可能几个百分点（本机在走 OpenCL 回退），不值得为它排期 |
| 降压降温换频率 | ⚠️ 79–80 °C、2745/3105 MHz，理论上限 +13%，收益太小 |

**唯一数量级级别的杠杆是减少候选数**，不是换内核。这直接把设计重心推向「字典 + 规则 + 定向生成」，而不是「堆掩码」。

## 格式分级：按 1 小时能覆盖多少

| 级别 | 1 小时覆盖 | 模式 |
| --- | ---: | --- |
| **S 级** | ≥ 10¹² | ZipCrypto 全系（17200 / 17210 / 17220 / 17225）、PDF 1.1–1.3（10400） |
| **A 级** | 10⁹ – 10¹² | PDF 1.4–1.6（10500）、GPG（17010）、WinZip AES（13600）、TrueCrypt（6211）、Office 2007（9400） |
| **B 级** | 10⁷ – 10⁹ | RAR5（13000）、RAR3-hp（12500）、bcrypt（3200）、Office 2013（9600）、PDF 1.7 L8（10700）、**7-Zip（11600）** |
| **C 级** | < 10⁷ | BitLocker、FileVault2、LUKS、KeePass / 1Password 主库等高迭代容器 |

## 口令强度分级：与格式解耦

| 级 | 类型 | 候选量级 | 典型例子 |
| --- | --- | ---: | --- |
| **L0** | 公共弱口令 | 10³ | `123456`、`admin`、`password`、设备默认口令 |
| **L1** | 通用弱口令 | 10⁵ | top-10 万榜、`Pwdb_top-100000`、中文 top-1 万 |
| **L2** | 全量字典 + 规则变形 | 10⁷ – 10⁸ | rockyou(14M)、CrackStation(64M)、best64 / d3ad0ne 规则、字典+4 位数字 |
| **L3** | 个人结构化口令 | 10⁸ – 10¹⁰（**定向生成**） | 拼音昵称、姓名+生日、手机号、站点域名、`公司缩写+年份`、网络流行语 |
| **L4** | 高熵 | ≥ 10¹² | 随机 12+ 位混合、密码管理器生成 |

::: tip 最大的浪费是把 L3 当成 L4 放弃
L3 的候选量级虽然大，但**不是靠枚举得到的，是靠已知信息「生成」出来的**。判断一个口令是 L3 还是 L4，看的是「关于它的线索有多少」，不是「它看起来多随机」。本次实测里两个真实口令都是 L3：生成成本几乎为零，命中率却很高。
:::

## 攻防矩阵：预算内该做哪个

格子 = 预计耗时；**粗体 = 在预算内，应该做**。

| | L0 (10³) | L1 (10⁵) | L2 (10⁸) | L3 (定向 10⁸) | L4 |
| --- | --- | --- | --- | --- | --- |
| **S 级** (≥10¹²/h) | **秒** | **秒** | **秒** | **分钟** | 小时~放弃 |
| **A 级** (10⁹–10¹²/h) | **秒** | **秒** | **分钟** | **分钟~小时** | 放弃 |
| **B 级** (10⁷–10⁹/h) | **秒** | **秒** | **~1 小时** | **小时级（上限）** | 放弃 |
| **C 级** (<10⁷/h) | **秒** | **~1 小时** | 放弃 | 只验证候选 | 放弃 |

配套的掩码上限（预算 4 小时，含 `-O` 大致 +10%）：

| 级别 | 纯数字 | 纯小写 | 小写+数字 | 全字符集 |
| --- | --- | --- | --- | --- |
| S 级 | 13 位 | 9 位 | 8 位 | 6 位 |
| B 级（RAR5，单 hash ≈119 kH/s） | 9 位（≈2.3 h） | 5 位 | 5 位 | 4 位 |
| B 级（7-Zip ≈26 kH/s @10 字符） | 8 位（≈1.1 h） | 5 位 | 5 位 | 4 位 |

::: warning 换算时注意两个陷阱
- **同一格式在不同口令长度下速度不同**（7z 尤其明显，见上）。
- **多 hash 同跑会被盐数摊薄**：两个 RAR5 一起跑只有 ~44 kH/s，单跑 119 kH/s。排期时按「单 hash 单任务」算。

按此换算：10 位纯数字在 RAR5 上 ≈ 23 h、在 7-Zip 上 ≈ 10.7 h，**都超预算 → 直接判不做**，除非有线索给出前缀或结构。中国手机号 `1[3-9]xxxxxxxxx`（9×10⁹）在 RAR5 上约 21 h，同样不做。
:::

## 社工决策树：从「来源 + 内容」推「口令类型」

这节才是真正省时间的地方。加密文件本身携带大量线索，先读它，再决定跑什么。

### 特征 → 推断表

| 观察到的特征 | 高概率口令类型 | 生成策略 |
| --- | --- | --- |
| 来自**资源站 / 论坛 / 网盘分享**（内容含 `.url`、`readme.txt`、「解压密码」字样） | 站点域名、站名+数字 | 对 top-10 万字典批量加 `.com/.cn/.net/.org` 后缀；再试 `站名`、`站名123`、`站名.com` |
| 内容为**源码 / 项目备份**（`.git`、`package.json`） | 项目名、版本号、作者 ID | `项目名`、`项目名+版本`、`作者名+123`、git 仓库名 |
| 内容为**个人相册 / 证件 / 简历** | 姓名拼音、生日、手机号、QQ / 微信 | 姓名全拼 / 首字母 × 生日(`YYYYMMDD`/`YYMMDD`/`MMDD`) × 手机号后 4/6/8 位 × 常见后缀 |
| 内容为**公司内部文档**（表格、制度、CAD） | 公司缩写+年份、工号、默认口令 | `缩写+年份`、`缩写@年份`、默认口令表 |
| 内容为**中文网络内容 / ACG** | 网络流行语、拼音昵称、动漫名 | 中文流行语 / ACG 词表；拼音全拼 + 首字母缩写 |
| 内容为**数据库 / 服务器备份** | 服务名+端口、默认口令 | `mssql`、`root`、`sa`、中间件默认口令表 |
| **文件名是中文** | 口令也可能是中文短语 | 中文词表 + 拼音变体 |
| 创建时间 = 打包时间 | 年份 / 日期 / 时间戳 | `YYYY`、`YYYYMMDD`、`YYMMDD`、时间戳前 8 位 |
| **对方是熟人 / 同事** | 与本人强相关 | 词典化：姓名、昵称、宠物、纪念日、口头禅 |

### 打分排序

对每个候选口令类别算：

```text
优先级得分 = P(口令属于该类 | 已知证据) / log10(生成成本)
```

- `P` 由上面的特征表给出（资源站 → 域名类 P 高；公司文档 → 默认口令 P 高）
- `生成成本` = 该类要试的候选数（L0=10³、L1=10⁵、L2=10⁸、L3 定向=10⁶~10⁸）
- 再除以**该格式的单候选成本**（S 级几乎为 0，B 级很贵）

结论：**格式越慢，越要把预算压到 P 最高的那一类上。** 对 B 级（RAR5 / 7z），永远先跑「P 最高的 1 万条定向候选」，而不是 rockyou 全量。

## 时间预算怎么花（单包 4 小时）

| 阶段 | 预算 | 内容 |
| --- | ---: | --- |
| P0 侦察 | 0 | 判算法、读 hash 元数据、看文件名 / 时间 / 来源 |
| P1 探针 | ≤ 10 s | 已知口令、名称 / 时间派生、top-1 千、站点域名规则 |
| P2 快速字典 | ≤ 15 min | top-10 万 + best64 规则 + 混合（字典 + 1~4 位数字） |
| P3 主力 | ≤ 2 h | 大字典（rockyou / CrackStation）+ 规则；掩码按上面的上限 |
| P4 定向 / 兜底 | ≤ 1.5 h | 社工定向字典、ZipCrypto 已知明文攻击、横传复用 |
| 收尾 | ≤ 10 min | 验证闸门 + 写结论 |

**阶段之间可提前结束**：任何阶段命中即跳到验证与横传。

## 执行流水线

```text
P0 侦察
 ├─ 7z l -slt <归档>            → 是否加密 / Method(AES) / 文件名 / 时间
 ├─ 提取 hash（zip2john / rar2john / 7z2john）
 ├─ 读 hash 元数据：$7z$ 的第 2 字段 = NumCyclesPower（<19 说明更快）
 └─ 产出「口令画像」：来源 + 内容类型 + 语言 + 时间 + 格式级

P1 探针（秒级，所有格式都跑）
 ├─ 已解出口令库（横传）
 ├─ 文件名 / 目录名 / 时间戳 / 年份 派生
 ├─ top-1000 + 站点默认口令
 └─ [ZipCrypto 专属] bkcrack 已知明文攻击（有 ≥12 字节已知明文即可）

P2 快速字典（分钟级）
 ├─ top-10 万 + best64 规则
 └─ 混合：字典 + 1~4 位数字后缀

P3 主力（小时级）
 ├─ S/A 级：rockyou → CrackStation → 大字典 + 规则 → 掩码（按上限）
 └─ B/C 级：只跑「P 最高」的定向字典，掩码严格按上限，超预算即停

P4 定向社工 / 兜底
 ├─ 按特征表生成定向字典（域名、拼音、生日、公司缩写…）
 └─ 仍不中 → 判「不做」，写清结论与已排除的空间

每阶段结束 —— 验证闸门（强制）
```

## 验证闸门（强制，不可跳过）

::: danger 铁律：校验通过 ≠ 密码正确
ZipCrypto 的 `$pkzip2$` 哈希只带 20 字节，校验很弱；而且归档可以被**刻意构造成双密码**——两个完全不同的口令都能通过完整 CRC32 校验。

这不是理论担忧。实测样本里，两个不同的 13 字节明文撞了同一个 CRC32 `0xEC2A11E6`，Python `zipfile` 对两个口令都放行。只看 hashcat 的 `Recovered` 就下结论，会把诱饵口令当成答案。

完整案例见 [hashcat 实战复盘](./hashcat实战复盘.md)。
:::

1. **不看 hashcat 的 `Recovered` 就下结论。** 必须解出明文再判。
2. **验证明文合理性**：可打印字符占比、是否符合已知明文、是否有预期文件结构。
3. **多候选全过校验时按「明文可读性」择优**，不要取第一个。
4. **每个候选都要用真实解压工具复核**（`7z t -p<pw>` + 解出内容比对）。
5. **不做「某 hash 已破解 → 跳过后续攻击空间」的记账**。要按 `(hash, 攻击空间)` 记账——踩坑实录里正因此把一个 5 秒能出的口令白白跳过了。
6. **解出一个口令立刻横传给其他所有未破包**（同一批归档复用同一口令是常态）。

## 工程约束清单

| 坑 | 规避方式 |
| --- | --- |
| hashcat 必须在自身目录运行 | 先 `cd` 到 hashcat 目录，否则报 `./OpenCL/: No such file or directory` |
| `-a 3` / `-a 6` 只接受**一个** hash 文件 | 同模式多个 hash 先合并成单个文件 |
| 多 hash 文件在 `-a 0` 下速度会被盐数摊薄 | 单包单任务，或接受摊薄 |
| 短跑测速不可信（autotune 占大头） | 测速用 ≥10⁶ 候选 |
| `hashcat -b` 的 7z 数字偏乐观 | 按口令长度用公式换算 |
| hashcat 11600 破不了含中文的 7z 口令 | 模块用朴素 UTF-16 转换，属硬限制（实测 pure 与 `-O` 内核都失败）；转 CPU 端验证 |
| 字典覆盖 ≠ 公开字典齐全 | 中文短语 / 拼音昵称 / 域名风格必须**定向补**，不是堆量，见 [密码字典从哪来](./密码字典从哪来.md) |

## 命令模板

```powershell
cd <hashcat目录>

# P1 探针
.\hashcat.exe -m 13000 -a 0 target.hash probe.txt -O -w 3

# P2 快速字典 + 规则
.\hashcat.exe -m 13000 -a 0 target.hash top-100000.txt -r rules\best64.rule -O -w 3

# P2 混合（字典 + 4 位数字）
.\hashcat.exe -m 13000 -a 6 target.hash top-10000.txt ?d?d?d?d -O -w 3

# P3 掩码（从短到长，先吃便宜的长度）
.\hashcat.exe -m 11600 -a 3 target.hash ?d?d?d?d?d?d?d?d -O -w 3 -i --increment-min 1 --increment-max 8

# 验证闸门：真实解压复核
7z t -p<candidate> <归档>
```

::: warning `-O` 不是免费加速，去掉它也不是万能药
`-O` 用优化内核换约 10% 速度，但会限制口令长度 ≤ 20 字节，并且**对内部使用 UTF-16 的算法可能产生假阴性**（hashcat 上游 `docs/limits.txt` 明确写了这点）。遇到「已知口令却破不了」，值得先去掉 `-O` 重跑一次。

但**不是所有情况去掉 `-O` 都能解决**：`-m 11600`（7-Zip）在 pure kernel 里用的也是同一套朴素 UTF-16 转换（`make_utf16le_S`），对 `> 0xFF` 的字符是硬限制，加什么编码参数都救不回来。详见 [hashcat 实战复盘](./hashcat实战复盘.md)。
:::

## 一页速查

```text
先判算法 → 再定格式级(S/A/B/C) → 再猜口令级(L0–L4) → 查矩阵 → 在预算内就做，超了就停

格式级决定「能试多少」，口令级决定「该试什么」，社工决定「先试哪个」。
慢格式上：永远先跑 P 最高的 1 万条定向候选，不要先跑掩码。
每命中一次：验证明文 → 横传其他包 → 记账。
```
