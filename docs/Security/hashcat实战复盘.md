---

> **结论先行**：这次跑了一整轮 hashcat，最后发现**最重要的那个口令是被自己的脚本跳过的**——一个 4.9 秒就能解决的事，因为采信了一个误报，被写进了错误结论。
>
> 三条可复用的教训：
>
> 1. **hashcat 报 `Recovered` 不等于破解成功。** 样本里存在被刻意构造的「双密码」归档，两个不同口令能同时通过完整 CRC32 校验。
> 2. **「某个 hash 已破解」不能当作「这个攻击空间搜完了」。** 要按 `(hash, 攻击空间)` 记账。
> 3. **误报的代价不是多跑几分钟，是让后续所有攻击被跳过。**

## 头号问题：采信了未验证的破解结果

### 发生了什么

`测试文件1.zip` 用模式 `17210` 跑，hashcat 报出了一个 `Recovered`。脚本立刻把它标记为「已破解」，然后——因为 `Run-Mask` 里有 `all cracked → skip` 逻辑——**把后续所有 ZIP 掩码全部跳过了**，日志里只留下一行：

```text
mode 17210 : all cracked, skip mask [zip-lower7]
```

补跑那个被跳过的 `?l`×7 掩码，**4.9 秒**（26.3 GH/s）就得到了真正的口令。

一个 5 秒钟就能解决的包，因为一个误报被彻底放弃，而且被写进了错误结论。

### 为什么 `17210` 会误报

hashcat 的 `-m 17210` 只能从 `zip2john` 拿到 **20 字节**（12 字节加密头 + 8 字节密文），**无法校验完整 CRC32**，只剩 1 字节头校验。hashcat 自己就警告过：

```text
This hash-mode is known to emit multiple valid candidates for the same hash.
```

`--example-hashes` 里这个模式也标着 `Keep.Guessing: Yes`。

### 但这不是普通误报——这个包是刻意构造的

用 Python `zipfile` 复核，发现两个口令**都能通过完整 CRC32 校验**：

| 候选 | 解出的明文 | 长度 | CRC32 | Python 校验 |
| --- | --- | ---: | --- | --- |
| 口令 A（真实） | `1111222233333` | 13 字节 | `0xEC2A11E6` | ✅ 通过 |
| 口令 B（诱饵） | 另一段 13 字节二进制 | 13 字节 | `0xEC2A11E6` | ✅ 通过 |

归档本身的元数据是 `CRC=0xEC2A11E6 size=13 compress_type=0(Stored) flag=0x0001(加密)`。

**两个完全不同的 13 字节明文，CRC32 完全相同。** CRC32 是线性的，给定一个串构造第二个同 CRC 的串并不难——这不是巧合，是测试样本本身的设计。

::: danger 这就是为什么验证闸门是铁律
`CRC32 校验通过 ≠ 密码正确`。唯一可靠的判据是**解出来的内容是否符合预期**：

- 是不是可读文本？可打印字符占比多少？
- 是否符合已知的明文 / 文件结构？
- 有没有别的候选也通过了校验？如果有，按「明文可读性」择优，而不是取第一个。
:::

## 其他三条教训

### 提前停止：最有希望的阶段没跑到

真正可能命中的阶段（CrackStation 6400 万、tier4 大字典、规则攻击、混合攻击、定向字典）都在队列后段，任务在 `maskdeep` 阶段就被停了。其中 CrackStation 对 RAR5 的遍历跑到一半被中断。

**排期时要把「最可能命中的」放前面，不是把「最容易写的」放前面。** 掩码最容易写，但在这批样本里恰恰最不可能命中。

### 攻击顺序不符合「慢哈希」的实际

| 模式 | 字典速度 | 掩码速度 |
| --- | ---: | ---: |
| 17210 PKZIP | ~3.6 GH/s | 最高 ~26 GH/s |
| 13000 RAR5 | ~44 kH/s（双 hash 同跑） | ~111 kH/s |
| 11600 7-Zip | ~11–18 kH/s | ~11–18 kH/s |

`?l`×7（26⁷ = 8.03×10⁹）在三者上的耗时：

| 模式 | `?l`×7 耗时 |
| --- | ---: |
| 17210 | **约 5 秒** |
| 13000 | 约 20 小时 |
| 11600 | 约 6 天 |

却把大量 GPU 时间投在**慢哈希的纯数字掩码**上（RAR5 `?d`×8 单项约 1 小时、7z `?d`×8 约 2.8 小时），而真实口令是 7 位小写、域名、中文短语——**这类空间恰恰最不可能命中**。

纯数字假设只对其中一个包成立。

### 工具硬限制：7z 模式与 CJK 口令（已定位到源码）

用 7-Zip 自建一个口令为中文短语的 7z（`7z t -p中文口令测试` 返回 `Everything is Ok`，换错误口令返回 exit=2，正负对照都做了），再用 hashcat 试，**所有编码方式都失败**：

| 候选编码方式 | 结果 |
| --- | --- |
| 原始 UTF-8 字节 | ✗ |
| 原始 UTF-16LE 字节 | ✗ |
| 原始 GBK 字节 | ✗ |
| `--hex-wordlist` + UTF-8 / UTF-16LE / GBK | ✗ |
| `--encoding-from utf-8 --encoding-to utf-16le` | ✗（候选人确实被转成了真 UTF-16LE 字节，仍然不中） |

John 1.9.0-jumbo-1 的 7z 格式在本机同样无法命中（连 ASCII 口令的自建包都 0 cracked），不能作为替代方案。

#### 为什么不行：不是 `-O`，是模块自己的朴素转换

hashcat 7.1.2 的 `OpenCL/m11600-pure.cl` 里，口令直接走：

```c
sha256_update_utf16le_swap(&ctx, w, pw_len);
```

而 `sha256_update_utf16le_swap` 调的是 `inc_common.cl` 的 `make_utf16le_S` —— 正是 hashcat 官方 `docs/limits.txt` 里描述的那种「**每隔一个字节插一个 `0x00`**」的朴素转换。

这个转换**只对单字节字符（≤ `0xFF`）成立**。中文是多字节 UTF-8，插零之后得到的字节序列并不等于 7z 真正要的 UTF-16LE 码元。

::: danger 关键点：`-O` 不是元凶
**pure kernel 和 optimized kernel 用的是同一套朴素转换**，所以这不是优化内核引入的假阴性，而是 `-m 11600` 对 `> 0xFF` 字符的硬限制。

实测证据（同一台机器、同一份 hash）：

| 组 | 条件 | 结果 |
| --- | --- | --- |
| A | 对照：纯 ASCII 口令 | ✅ `Recovered 1/1` —— 管线本身是好的 |
| B | 中文口令，**不带** `-O`（Pure Kernel） | ❌ `Exhausted 0/1` |
| C | 中文口令，**带** `-O`（Optimized Kernel） | ❌ `Exhausted 0/1` |
| D | 中文口令 + `--encoding-to utf-16le` | ❌ `Exhausted 0/1`，回显 `$HEX[2d4e8765e353e44e4b6dd58b]`（确实是正确的 UTF-16LE 字节） |

D 组尤其能说明问题：**即使把正确的 UTF-16LE 字节喂进去，模块还会在它上面再做一次朴素转换**（双重转换），结果必然错。任何字典或编码参数都救不回来。
:::

::: warning 别被 `limits.txt` 带偏
hashcat 的 `docs/limits.txt` 写着：

> Since hashcat v6.2.1 there is true UTF-16 support for pure kernels. UTF-16 is fully supported.
> This applies to optimized kernels (`-O`) only …

那条讲的是**通用** UTF-16 支持。具体到 `-m 11600`，模块自己绕开了通用路径、直接调朴素转换函数，所以「去掉 `-O` 就好了」在这里**不成立**。

判断某个模式到底支不支持 UTF-16，**得看模块源码，不能只看 `limits.txt`**。这条正好是个反例。
:::

#### 那 CJK 口令的 7z 怎么办

只能走 CPU 端验证：`7z.exe t -p<candidate>`，或 `py7zr` 遍历候选表。适合几千到几万条的**定向**表，不适合上亿条。

这反过来又强调了 [优先级设计](./压缩包破解优先级.md) 里的那条：慢格式上要先把预算压到「P 最高的那一小撮候选」，因为兜底的暴力路径可能压根不存在。

## 改进方案

### P0 — 给每个「破解成功」加验证闸门

1. **不只看 `Recovered`，必须验证明文内容**：
   - ZIP：用 Python `zipfile.read(pwd=...)` 读出，检查可打印性 / 与已知明文比对
   - 7z / RAR：`7z t -p<pw>` 且解出文件后校验内容与 CRC
   - 多个候选都通过校验时，按「明文是否可读、是否符合已知明文」择优
2. **对 `Keep.Guessing: Yes` 的模式**（17200 / 17210 / 12500 等）：加 `--keep-guessing` 收集**全部**通过校验的候选，而不是第一个就收工；再用「解密结果的可读性 / 熵 / 预期格式」二次筛选。
3. **已知明文的场景**（本次五个包内容相同）可以直接用 **bkcrack** 做 ZipCrypto 已知明文攻击拿到内部密钥，用来判定候选真伪，完全绕开弱校验。

### P0 — 修掉「提前判死」的逻辑

- 不要用「某个 hash 已破解」当作「该攻击空间已搜索完毕」。
- 正确做法：每个 hash 一个独立 hash 文件 + 独立 potfile；或者按 `(hash, mask/wordlist)` 记账，只跳过真正跑过的组合。

### P1 — 慢哈希的攻击顺序

- RAR5 / 7z 先跑：小字典（≤10 万）→ 规则（best64 / InsidePro）→ 混合（字典+后缀）→ 定向字典；**最后**才考虑掩码。
- 掩码只在有证据时才投入大空间（例如同批已解出的包是纯数字）。

### P1 — 字典要「定向扩」，不是「堆量」

- **拼音**：全拼 + 首字母缩写 + 常见昵称写法
- **站点 / 域名风格**：对现有字典批量施加 `$X .com` 之类规则即可大幅扩展
- **中文网络流行语 / ACG 词表**：公开库里几乎没有，得自己整理
- 用规则放大：`best64`、`InsidePro-PasswordsPro`、`dive`、`T0XlC`

### P2 — 工程化

- potfile + 分阶段脚本已经具备续跑能力；**停止前把当前阶段结论落盘**。
- 每阶段结束自动执行一次「跑出的口令 → 对所有未破包复用」。本次实现了复用函数，但应该在每次掩码 / 字典后都跑。
