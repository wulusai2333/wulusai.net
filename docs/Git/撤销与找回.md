---
title: 撤销与找回
---

> **最短路径**：先判断你的改动停在哪一层，再挑对应的一条命令。90% 的情况是这四条：
>
> | 你的处境 | 命令 |
> | --- | --- |
> | 改了文件还没提交，想还原 | `git restore <文件>` |
> | 已经 `git add` 了，想撤出暂存区（保留改动） | `git restore --staged <文件>` |
> | 最后一次提交写错了（还没推送） | `git commit --amend` |
> | 提交"没了"／误删了分支 | `git reflog` 找回来 |
>
> 下面全部命令都在 **git 2.56.0.windows.2 / 2026-10** 实机验证过，输出是真实的。

## 先分清四个位置

撤销类操作之所以容易搞混，是因为没分清改动停在哪儿。Git 有四层：

| 位置 | 说明 | 通俗说法 |
| --- | --- | --- |
| **工作区** | 你正在编辑的文件 | 还没告诉 Git |
| **暂存区**（index） | `git add` 之后待提交的内容 | 已经排好队 |
| **本地仓库** | `git commit` 之后的提交 | 写进历史了 |
| **远程仓库** | `git push` 之后 | 别人也能看到了 |

**撤销的难度从左到右递增**：工作区最随意，推送出去之后就很难干净地收回。判断清楚在哪一层，命令就不用背。

## 改坏了，但还没提交

### 改了文件想还原

```bash
git status --short     # 先看有哪些改动
git restore a.txt      # 丢弃这个文件的改动
```

真实输出（` M` 表示工作区已改、未暂存）：

```text
$ git status --short
 M a.txt
$ git restore a.txt
$ git status --short
```

::: tip restore 是 git 2.23 引入的新命令
它替代了老写法 `git checkout -- <文件>`。`checkout` 一个命令身兼数职（切分支、切提交、还原文件），语义混乱到 Git 官方都承认是个设计失误，所以拆成了 `git switch`（切分支）和 `git restore`（还原文件）。新代码请用新命令。
:::

### 已经 add 进暂存区了

`--staged` 只把内容从暂存区拿回工作区，**改动本身不丢**：

```bash
git restore --staged a.txt
```

真实输出（`M ` 表示已暂存，` M` 表示已退回工作区）：

```text
$ git add a.txt
$ git status --short
M  a.txt
$ git restore --staged a.txt
$ git status --short
 M a.txt
$ cat a.txt
changed
```

### 误删了已提交的文件

```bash
git restore b.txt
```

```text
$ rm b.txt
$ git status --short
 D b.txt
$ git restore b.txt
$ ls
a.txt  b.txt  c.txt
```

只要文件进过提交，就永远能从历史里捞回来 —— 这是 Git 最让人安心的一点。

## 提交写错了，但还没推送

### 只是说明写错了

```bash
git commit --amend -m "改过的说明"
```

```text
$ git commit --amend -m "init: 第一个提交（改过的说明）"
[master 78eed47] init: 第一个提交（改过的说明）
 Date: Tue Oct 20 04:01:54 2026 +0800
 2 files changed, 2 insertions(+)
```

### 漏了文件，但不想改说明

`--no-edit` 表示沿用原来的提交信息：

```bash
git add c.txt
git commit --amend --no-edit
```

```text
$ git log --oneline --stat -1
a921914 init: 第一个提交（改过的说明）
 a.txt | 1 +
 b.txt | 1 +
 c.txt | 1 +
 3 files changed, 3 insertions(+)
```

::: warning 坑：`--amend` 不是修改，是"换一个提交"
它生成一个**全新的提交**（新的 SHA），老提交被丢进回收站（reflog）。所以：
- 本地随便用，无所谓；
- **已经推送过就别用**（除非你确定没人基于它工作），因为历史被改写了，正常 `push` 会被拒绝。
:::

## 想整个撤掉最后一次提交：reset 的三种模式

这是最容易记混的地方。三种模式的区别只有一个问题：**撤销的范围到哪一层为止。**

| 模式 | 移动 HEAD | 重置暂存区 | 重置工作区 | 结果 |
| --- | --- | --- | --- | --- |
| `--soft` | ✅ | ❌ | ❌ | 提交没了，改动**全在暂存区** |
| `--mixed`（默认） | ✅ | ✅ | ❌ | 提交没了，改动**退回工作区** |
| `--hard` | ✅ | ✅ | ✅ | 提交没了，**改动直接消失** |

同一个场景（一个提交 + 一处未暂存改动 + 一个已暂存新文件），三种模式的真实差别：

```text
—— 起点 ——
$ git status --short
 M a.txt
A  e.txt
$ git log --oneline
4ec0e31 第二个提交
a921914 init: 第一个提交（改过的说明）

—— reset --soft HEAD~1 ——
$ git status --short
 M a.txt
A  d.txt        ← 提交里的改动，全部回到暂存区
A  e.txt

—— reset --mixed（= git reset HEAD~1，默认）——
$ git status --short
 M a.txt
?? d.txt        ← 从暂存区退回工作区，成了未跟踪文件
?? e.txt

—— reset --hard HEAD~1 ——
$ git status --short
$ ls            ← 新增文件连同改动一起没了
a.txt  b.txt  c.txt
```

::: danger `--hard` 会真的删掉未提交的改动
它不问你、不备份。执行前先 `git status` 看清楚，或者干脆先 `git stash`。
**但只要曾经提交过，就还能救** —— 见下一节。
:::

## 提交"丢了"怎么找回来：reflog

`git reflog` 记录的是**本地 HEAD 的每一次移动**，包括 commit、reset、checkout、amend。它和 `git log` 的区别：

- `git log` 只看当前分支的祖先链 —— 被 reset 掉的提交不在链上，看不到；
- `git reflog` 看的是"我这一段时间都干了什么"，**被丢弃的提交还在这里**。

刚才 `reset --hard` 丢掉的那个提交：

```text
$ git reflog --oneline
a921914 HEAD@{0}: reset: moving to HEAD~1
2b339ad HEAD@{1}: commit: 第二个提交        ← 就是它
a921914 HEAD@{2}: reset: moving to HEAD~1
...

$ git show --stat --oneline 2b339ad
2b339ad 第二个提交
 a.txt | 2 +-
 d.txt | 1 +
 e.txt | 1 +

$ git reset --hard 2b339ad                  ← 恢复
HEAD is now at 2b339ad 第二个提交
```

思路固定是三步：**reflog 找到丢失提交的 SHA → `git show` 确认内容 → `git reset --hard <SHA>` 回去**。

### 误删了分支，也是同一招

```text
$ git branch -D feature/lost
Deleted branch feature/lost (was 590e54c).

$ git reflog --oneline
590e54c HEAD@{1}: commit: feat: 分支上的工作    ← 分支上那个提交还在

$ git branch feature/lost 590e54c              ← 用 SHA 重建分支
$ git branch
  feature/lost
* master
```

::: warning reflog 不是永久的
默认只保留 **90 天**（不可达对象由 `gc` 回收，默认 30 天）。`reflog` 本身也只在本地存在 —— 换台机器就没有了。所以这套是"刚出事时的急救"，不是备份方案。
:::

## 已经推送出去的提交写错了：用 revert

**原则：已经推送的历史不要改写，用一次新的提交去抵消它。**

```text
$ git revert --no-edit HEAD
[master f380152] Revert "feat: 一个有问题的提交"
 1 file changed, 1 deletion(-)
 delete mode 100644 bug.txt

$ git log --oneline -3
f380152 Revert "feat: 一个有问题的提交"     ← 多了一个反向提交
730646b feat: 一个有问题的提交
a921914 init: 第一个提交（改过的说明）
```

好处：历史完整、别人拉下来不会炸、不需要任何人配合。

### 什么时候才轮到强推

只有一种情况值得强推：**这个分支只有你在用，而且你刚推上去就发现错了**（比如把密码提交上去了）。

```bash
git push --force-with-lease origin master
```

**用 `--force-with-lease`，不要用 `-f`。** 区别：`-f` 是无脑覆盖远端；`--force-with-lease` 会先检查"远端还是不是我上次看到的那个样子"，如果别人期间推过东西，它就拒绝：

```text
$ git push --force-with-lease origin master
To ~/remote.git
 ! [rejected]        master -> master (stale info)
error: failed to push some refs to '~/remote.git'
```

这个"失败"正是它的价值 —— 它挡住了你覆盖别人工作的手。

## 把文件恢复成历史某个版本

```bash
git restore --source=HEAD~1 r.txt     # 回到上一个提交的版本
git restore --source=<某个SHA> r.txt  # 回到任意提交
```

```text
$ cat r.txt
v3
$ git restore --source=HEAD~1 r.txt
$ cat r.txt
v2
$ git status --short
 M r.txt        ← 恢复结果变成了一个未提交的改动，不会自动提交
```

## 速查表

| 想做的事 | 命令 | 危险度 |
| --- | --- | --- |
| 丢弃某文件的未提交改动 | `git restore <文件>` | ⚠️ 改动没了 |
| 把文件移出暂存区 | `git restore --staged <文件>` | 安全 |
| 恢复被删的文件 | `git restore <文件>` | 安全 |
| 改最后一次提交说明 | `git commit --amend -m "..."` | ⚠️ 换 SHA，别对已推送的用 |
| 补文件进最后一次提交 | `git add <文件> && git commit --amend --no-edit` | 同上 |
| 撤销最后一次提交、保留改动 | `git reset --soft HEAD~1` | 安全 |
| 撤销最后一次提交、退回工作区 | `git reset HEAD~1` | 安全 |
| **彻底丢弃**最后一次提交和改动 | `git reset --hard HEAD~1` | ☠️ 未提交的改动会消失 |
| 找回过早前的提交 | `git reflog` + `git reset --hard <SHA>` | 安全 |
| 恢复误删分支 | `git branch <名> <SHA>` | 安全 |
| 撤销一个已推送的提交 | `git revert <SHA>` | 安全 |
| 覆盖远端历史（慎用） | `git push --force-with-lease` | ☠️ 会覆盖别人的提交 |
