---
title: 本地大模型怎么选
---

本地跑大模型这件事，最大的时间浪费不是下载模型，而是**先用错工具、再去换工具**。这篇只讲一件事：什么场景该用哪条路线。功能清单到处都有，取舍结论才是这里要写的东西。

## 最短路径

80% 的情况只需要记住这几步：

1. **想快点用上** → 装 Ollama，`ollama run <模型名>`，结束。别去看编译选项。
2. **想要图形界面调参数** → 装 LM Studio，它本质也是 llama.cpp，只是套了壳。
3. **想抠显存/速度/量化细节** → 直接用 llama.cpp，自己控制 `-ngl`、`-c`、量化档位。
4. **要给别人用、要并发** → vLLM，其他三个都不是这个赛道的。

::: tip 先想清楚你在做哪一种
「**自己用**」和「**提供 API 服务**」是两种完全不同的需求，选型差异比「谁的 benchmark 高」大得多。前者拼的是省事，后者拼的是吞吐和并发。
:::

## 为什么不是「四个工具比功能」

它们不是同一层的东西，放一张表里比「谁快」没有意义：

| 路线 | 它其实是什么 | 什么时候用 | 什么时候别用 |
| --- | --- | --- | --- |
| **llama.cpp** | 推理引擎（C/C++），GGUF 格式的事实标准 | 想在本地把量化、层数、上下文抠到极致；硬件是 CPU / Apple Silicon / 消费级显卡 | 不想编译、不想看命令行参数 |
| **Ollama** | llama.cpp（近年也接别的后端）+ 模型管理 + 常驻服务 | 单人本地日用、写脚本调 API、快速切换模型 | 需要高并发；想精确控制每个推理参数 |
| **LM Studio** | 图形界面的 llama.cpp 封装 + 本地 OpenAI 兼容服务 | 不想碰命令行；要试不同模型；要一个「可视化调参台」 | 想脚本化、自动化；服务器 / 无桌面环境 |
| **vLLM** | 面向吞吐的 GPU 推理服务（PagedAttention、连续批处理） | 多人共用、要并发、要吞吐；有像样的 GPU | 单人本地玩；没独显；显存吃紧 |

一句人话：**Ollama 和 LM Studio 是给你用的，vLLM 是给一群人用的，llama.cpp 是给愿意拧螺丝的人用的。**

::: warning LM Studio 与 Ollama 的关系
两者底层都大量使用 llama.cpp 的成果，所以「Ollama 比 LM Studio 快」这类说法通常没有意义 —— 决定速度的是**同一份权重、同一个量化档位、同样的层数卸载策略**，换壳子不改变这些。真正能拉开差距的是 vLLM 这一类为批处理专门设计的服务。
:::

## 按硬件条件的决策表

这张表是这篇最核心的部分，按你手上的机器查：

| 你的情况 | 选它 | 为什么 |
| --- | --- | --- |
| 只有 CPU / 核显，内存 16G 以上 | llama.cpp 或 Ollama，小参数模型 + Q4 量化 | 无 GPU 时唯一现实的路；参数越大量化档位要越低 |
| Apple Silicon（统一内存） | Ollama / LM Studio | 统一内存没有「显存不够」这个概念，能吃下比同价位独显更大的模型；Metal 后端开箱可用 |
| 单张消费级 N 卡，只想聊天 | Ollama | 自动卸载层数，不用手工试 `-ngl` |
| 单张消费级 N 卡，要精确控制 | llama.cpp | 能逐项调层数/上下文/KV 量化，这些决定了「能不能跑起来」 |
| 只是想试很多模型 | LM Studio | 图形界面下载、切换、对比，比命令行试错快 |
| 要多人并发 / 对外提供 API | vLLM | 连续批处理与分页 KV 缓存是它的主场，llama.cpp 系列不是为这个设计的 |
| 要长期跑、当服务用 | vLLM，或 Ollama 但明确它不是并发方案 | 常驻服务要考虑显存预分配、上下文长度上限、请求排队 |

## 量化档位：Q4_K_M / Q5_K_M / IQ 系列怎么选

GGUF 文件名后缀就是量化档位。命名规则（按 llama.cpp 的定义）：

- 数字是**基础位宽**：`Q4`≈4 bit，`Q5`≈5 bit，`Q8`≈8 bit。位宽越低文件越小、质量越差。
- `_K` 是 K-quant 的超级块方案（比早期的 `Q4_0` 新，通常同体积下质量更好）。
- `_S` / `_M` 是同一位宽下的混合档次：`_M`（medium）会把一部分敏感张量提升到更高精度，所以比 `_S` 大一点、稳一点。
- `IQ` 是 i-quant，用非线性量化格点，通常配合重要性矩阵（imatrix），同体积下往往更小。

**结论先给：**

| 档位 | 体积（相对） | 质量 | 什么时候选 |
| --- | --- | --- | --- |
| **Q4_K_M** | 基准 | 日常够用 | **默认选项**。放得下就用它，别纠结 |
| **Q5_K_M** | 比 Q4_K_M 大 15% 上下 | 比 Q4_K_M 好，但差距不大 | 显存还有富余、且上下文也要塞得下时 |
| **Q6_K / Q8_0** | 明显更大 | 接近无损 | 显存非常多；或者要做「参照跑分」 |
| **IQ4_XS** | 略小于 Q4_K_M | 与 Q4_K_S 接近 | Q4_K_M **就差那么几百 MB** 放不下时的救场选项 |
| **Q4_K_S** | 略小于 Q4_K_M | 略差于 Q4_K_M | 异构后端下不想碰 i-quant，又缺一点显存 |
| **Q3 及以下** | 小得多 | 掉得很明显 | 实在没别的办法。参数更大的模型配 3 bit，有时反而强于小模型配 4 bit |

::: warning 数字都是「量级参考，未在本机验证」
上面这些量化档位的体积比例、以及「Q5 比 Q4 好多少」这类结论，来自 llama.cpp 官方工具与社区公开测量，**我没有在本机复现过**。不同模型架构（尤其是 MoE）的差距不一样，请把它当**方向性参考**而不是精确值。真要定档位，就同一份权重自己跑一遍对比。
:::

### 一个经常被忽略的坑：i-quant 不是无条件更快

`IQ4_XS` 文件比 `Q4_K_M` 小，但**不保证更快**。i-quant 的反量化计算量更大，在一些后端（社区反馈集中在部分非 CUDA 后端与 Apple Silicon）上可能比同体积的 K-quant 慢不少。

所以「显存就差一点」时的正确动作不是直接上 IQ，而是：

1. 先试 `Q4_K_S`（同为 4 bit K-quant，体积更小）；
2. 还不行再上 `IQ4_XS`，并**实际测一次生成速度**；
3. 如果慢了，回到 Q4_K_S 并降低上下文长度。

## 显存/内存怎么估

别背具体数字，记住**三块加起来**要放得进：

```text
总需求 ≈ 权重文件大小
       + KV cache（随上下文长度线性增长）
       + 运行时开销（计算缓冲区、图形界面等）
```

- **权重**：直接看你下载的那个 `.gguf` 文件多大，这是最准的。
- **KV cache**：和**上下文长度**成正比，也和层数、KV 头数有关。上下文翻倍，KV 大致翻倍。**很多人只算权重、不算 KV，于是模型加载成功、一提问就 OOM。**
- **运行时开销**：几百 MB 量级（未验证，视后端而定）。

::: tip 把上下文当显存来管
本地跑模型时，**上下文长度（`num_ctx` / `-c` / `--max-model-len`）和模型大小是同等重要的旋钮**。宁可模型大一点、上下文小一点，也不要上下文开满结果第一步就爆显存。
:::

## 模型权重放机械盘会拖慢加载

这是很值钱的一条，因为它**看起来不像性能问题**，很多人归因到「显卡不行」。

**现象**：冷启动加载模型要等很久；生成过程中偶发卡顿；换到 SSD 后同一模型明显变快。

**原因**：llama.cpp 默认用 `mmap` 把权重文件映射进内存，按需从磁盘读页。机械盘的**随机读**极慢，于是：

- 冷启动时不能顺序把文件读进来，而是边算边缺页；
- 系统内存紧张时页面被换出，下次用到再回读磁盘，就会在生成中途卡住。

**解法（按优先级）：**

1. **把模型放 SSD / NVMe**。这是一劳永逸的做法，也是最便宜的优化。
2. 内存足够时，用**锁内存**模式避免被换出：llama.cpp 的 `-lm, --load-mode` 支持 `mlock`、`mmap`、`mmap+mlock`、`dio`、`none`（`--load-mode` 是较新版本才有的参数，具体可选值请以你本地 `--help` 为准）。
3. 内存足够但不想用 mmap，可以试 `--load-mode none`：完整读入内存，加载更慢但之后没有缺页。
4. Ollama 用户：`OLLAMA_MODELS` 环境变量可以改变模型存放位置 —— **注意别把它指到一个机械盘上**。

::: danger 不要把 Ollama 的模型目录随手指向「空间大的那块盘」
`OLLAMA_MODELS` 最容易被指向存放数据的机械盘（因为那里空间大）。结果就是这篇里描述的坑：加载变慢、生成偶发卡顿，而且很难第一时间联想到磁盘。指向 SSD。
:::

## 报错原文与解法

::: warning 免责声明：以下报错信息未在本机复现
我**没有**跑这些命令的环境，下面的报错文本是按 llama.cpp / CUDA 常见报错写的**典型形状**（关键词和含义是准的，具体数字和措辞可能与你看到的略有出入）。请按「关键词」去匹配你自己的日志，不要逐字比对。
:::

| 报错（典型形状） | 原因 | 解法 |
| --- | --- | --- |
| `CUDA error: out of memory` / `failed to allocate ... buffer` | 权重 + KV cache 超出显存 | 降 `-ngl`；降 `-c`；换更低量化档位；关掉占显存的其他程序 |
| `llama_model_load: error loading model` / `unknown model architecture` | 模型架构太新，当前构建不支持 | 升级到较新的 llama.cpp 构建（官方 release 或自己编） |
| `failed to load model ... (exit code: -6)` 之类加载崩溃 | 多半是量化档位或文件损坏 | 校验文件大小/哈希，换一个量化档重下 |
| 模型明明放得下却只用了一部分 GPU | 层数没卸载够 | 提高 `-ngl`（较新构建可试 `-ngl auto`），让它按显存自动决定 |
| 输出被截断、答非所问 | **上下文长度不够**，提示被悄悄截断 | 提高上下文；检查客户端的上下文设置是否和引擎一致 |

## 报错排查的通用顺序

遇到「跑不起来」，按这个顺序排，比乱改参数有效：

1. **显存**够不够（权重 + KV + 开销）→ 不够就降档、降上下文、降层数；
2. **上下文**设置有没有对齐（客户端以为 32k、引擎只给 2k 是最常见的隐形故障）；
3. **量化档位**和硬件后端是否匹配（i-quant 在某些后端偏慢）；
4. **磁盘**：模型是不是在机械盘上；
5. 最后才怀疑模型本身。

## 几个容易踩的具体点

- **Ollama 的上下文默认值很小**。官方 Modelfile 文档写明 `num_ctx` 默认 **2048**。用 OpenAI 兼容接口对接现成客户端时，客户端往往假设上下文有几万 token，实际被截断到 2048 —— 表现为「模型好像没看见我前面说的话」。要显式设大 `num_ctx`。
- **模型别放在需要实时解压/加密的目录**（压缩盘、加密卷）：每次读页都要解压，比机械盘还慢。
- **杀软实时扫描**：首次加载一个几 GB 的 GGUF 文件时被全盘扫描，会让加载时间翻倍。给模型目录加白名单。
- **远程/网络盘**：把模型放在 NAS 或网络映射盘上用 mmap，随机读延迟是毫秒级，体验会非常差。
- **「参数大一定更好」不成立**：在固定显存下，一个更大的模型配更低量化，有时反而不如小一号模型配 Q4_K_M。**先保证量化档位在 Q4_K_M 以上，再考虑把参数堆大。**

## 把它接进你自己的程序

选完路线还不算完，多数人要的是「本地跑一个模型，然后用代码调它」。这里有个事实值得单独说：**Ollama 和 LM Studio 都提供了 OpenAI 兼容的 HTTP 接口**，所以你已经写好的、用云端 API 的那套代码，通常只改 `base_url` 和 `api_key` 就能切到本地。

```bash
# 本地服务通常长这样（具体端口以你安装的版本为准，未验证）
# Ollama      → http://127.0.0.1:11434/v1
# LM Studio   → http://127.0.0.1:1234/v1
# llama.cpp server → 默认监听 127.0.0.1（端口以你本地 --help 为准）
curl http://127.0.0.1:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <YOUR_API_KEY>" \
  -d '{
    "model": "<你的模型名>",
    "messages": [{ "role": "user", "content": "你好" }]
  }'
```

::: danger 换成本地接口后，最容易丢的就是「上下文长度」
云端模型的上下文往往是几万到几十万 token，而且**客户端默认值通常就是按这个假设来的**。切到本地之后：

- Ollama 的 `num_ctx` 官方默认是 **2048**（见官方 Modelfile 文档）；
- 而你的客户端很可能**照样发一个几万 token 的提示词**，或者照样假设「模型记得前面聊过什么」。

结果不是报错，而是**静默截断** —— 表现成「模型好像没看见我前面说的话」「长文档问答答得莫名其妙」。**切换本地服务后，第一件事就是把上下文长度显式对齐。**
:::

**几个自查动作**（比读文档快）：

1. 调一次接口，看**响应里报告的 token 数**是不是和你估计的一致 —— 差一个量级就说明上下文被砍了。
2. 塞一个「开头有标记、结尾有标记、中间填充」的长提示，问它开头的标记是什么。答不出来就是中间被截断了。
3. 本地服务的日志会打印实际加载的上下文长度，**以日志为准**，不要以客户端设置界面为准。

## 模型从哪来，以及别做的事

- **模型文件本身也是「坑点来源」**：同一份权重有 safetensors（训练/转换用）和 GGUF（推理用）两种常见形态，本地推理要的是后者。别把 safetensors 丢给 llama.cpp。
- **下载大文件要能续传**。几个 GB 的模型断了重下很痛，用支持断点续传的工具，并且**校验文件大小**再加载。
- **别把量化后的模型再量化**。想要更低档位就从原始权重重新量化，层层叠加只会更差。
- **量化需要原始精度权重**，这个过程对内存要求比推理高得多，别在一台刚好跑得动推理的机器上做量化。
- **许可证要看清**。有些模型权重只允许非商业使用，自己跑没事，一旦对外提供服务就是另一回事了 —— 这条比技术选型更容易出事。

## 官方文档与我的取舍

- llama.cpp：<https://github.com/ggml-org/llama.cpp>
- llama.cpp server 参数表（最全的 flag 清单）：<https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md>
- Ollama：<https://github.com/ollama/ollama> · Modelfile 参数：<https://github.com/ollama/ollama/blob/main/docs/modelfile.mdx>
- LM Studio：<https://lmstudio.ai/>
- vLLM 显存/性能调优：<https://docs.vllm.ai/en/stable/configuration/optimization>

我的取舍结论：

1. **默认 Ollama，需要拧参数时换 llama.cpp，两者不冲突**（Ollama 可以直接 `FROM ./本地.gguf` 导入你从别处下好的 GGUF）。
2. **LM Studio 的价值在「试」而不在「跑」**：用它快速判断某个模型值不值得留，定下来之后把 GGUF 拿走，用 llama.cpp 或 Ollama 长期跑。
3. **vLLM 的参数和前三者几乎不通用**，别把 `-ngl` 那套经验带过去。它的调优主轴是 `gpu_memory_utilization` / `max_model_len` / `max_num_seqs` / 张量并行。
4. 官方文档给的是**功能全貌**，判断「该不该用」还得回到硬件和并发需求 —— 也就是本文前面那两张表。

::: tip 适用范围
本文的前提是**自建推理**。如果你只是想用一个强模型解决问题、并不在乎数据是否离开本机，直接调云端 API 的成本（时间与金钱）通常远低于本地折腾。本地部署真正的理由是：数据不出本机、离线可用、长期零边际成本、以及可定制（微调、量化、私有工具链）。
:::
