---
title: 提示词与上下文工程
---

提示词的瓶颈很少是「措辞不够礼貌」，而是**上下文组织得让模型找不到重点**。这篇写面向开发者的四条经验：系统提示词写什么、少样本例子怎么放、长上下文里的「中间遗忘」、以及为什么要给模型「说不知道」的出口。

## 最短路径

80% 的情况只需要这四步：

1. **系统提示词**只写三样：角色与边界、输出格式、失败时怎么办。**不要写背景资料。**
2. **少样本例子**放在「规则之后、真实输入之前」，格式必须和期望输出**逐字一致**。
3. **重要的东西放两头**：开头（任务与规则）和结尾（再次强调 + 真实输入）。中间放资料。
4. **给出口**：明确写「如果资料里没有，就说没有」。不写，模型就一定会编。

::: tip 一句话原则
提示词工程的大部分工作，不是「教模型怎么做」，而是**「减少它需要做的猜测」**。每一条含糊之处，模型都会用编造来填补。
:::

## 系统提示词写什么

系统提示词是**长期有效的约束**，不是「本次任务的资料」。这个区分很重要 —— 把资料塞进系统提示词是很常见的错误。

应该写的：

| 内容 | 例子 | 为什么 |
| --- | --- | --- |
| **角色与领域** | 「你是严谨的技术资料问答助手。」 | 决定用词风格与默认假设 |
| **边界（不做什么）** | 「不提供法律/医疗建议；不做与检索无关的推测。」 | 边界比能力描述更能减少跑偏 |
| **输出格式** | 「先给结论一句话，再分点展开，总共不超过 200 字。」 | 格式约束的收益最直接、最稳定 |
| **失败时的行为** | 「资料中没有相关信息时，直接回答『资料中没有相关信息』。」 | 见本文最后一节 |
| **语气与粒度** | 「面向有经验的开发者，不解释基础概念。」 | 减少废话，提高信息密度 |

**不该写的：**

- **背景资料 / 长文档**。它们属于用户消息，而且应该只在真的相关时才放进去。
- **大量互相冲突的规则**。规则一多，模型会挑它「觉得重要」的执行 —— 通常不是你希望的那条。
- **没有边界的「尽量做好」**。「尽量」这个字对模型没有任何约束力。

```text
# 一份可直接用的骨架
你是 <角色>，服务于 <谁>。

【任务】
<一句话说清要产出什么>

【约束】
- <硬性边界 1>
- <硬性边界 2>

【输出格式】
<结构、长度、是否用 Markdown>

【资料不足时】
直接说明缺少什么，不要推测或用常识补充。
```

::: warning 规则要有优先级
多条规则冲突时，模型不会报错，它会**悄悄选一条**。所以：

- 规则数量控制在**能记住的范围内**（经验上 5～8 条以内，未验证）；
- 把最重要的那条**也写进任务描述里重复一次**，而不是只放在系统提示词里；
- 如果两条规则真的会冲突，在系统提示词里说清谁优先。
:::

## 少样本例子怎么放

少样本（few-shot）的本质是**用示例代替描述**。它对「格式」「风格」「边界判断」有效，对「知识」无效 —— 别想着用例子教会模型它不知道的事实。

### 位置

```text
[系统提示词：角色 + 规则 + 输出格式]
[少样本示例 1：输入 → 输出]
[少样本示例 2：输入 → 输出]
[少样本示例 N：输入 → 输出]
[真实输入]
```

**示例放在规则后面、真实输入前面。** 顺序颠倒是常见错误：先给例子再给规则，模型更倾向于模仿例子的**表面形式**，而不是遵守后面才出现的规则。

### 挑选原则

1. **格式必须逐字一致。** 例子的格式就是事实上的规格说明。如果例子里的字段大小写、标点、换行不统一，模型输出也会不统一。
2. **覆盖边界情况，而不是覆盖典型情况。** 一个模型大概率会做对的普通例子没有信息量；**一个容易做错的边角例子才值钱**。
3. **数量从 2～3 个起步。** 例子越多越占上下文，而且收益很快饱和。**没有任何通用最优数量** —— 你要自己试（未验证）。
4. **例子不能有错。** 模型会忠实学习例子里的每一个细节，包括错误。

::: danger 少样本示例是最容易被忽略的「格式污染」来源
如果你有 3 个例子，其中 2 个用 `-` 列表、1 个用 `*` 列表，输出就会在两种之间随机跳。**示例之间的一致性，比示例本身好不好更重要。**
:::

### 一个具体的对比

```text
# 效果差：只描述规则
把用户的话改写成搜索关键词。

# 效果好：用例子锚定格式
把用户的话改写成搜索关键词，用空格分隔，不加标点。

输入：vitepress 站内链接写错了会不会构建失败？
输出：vitepress 站内链接 构建失败

输入：本地跑大模型显存不够怎么办
输出：本地大模型 显存不足 解决

输入：这个怎么弄
输出：无法提取关键词
```

注意最后一个例子：它就是**「说不知道」的示例**。用示例教边界，比用一句话描述边界有效得多。

## 长上下文里的「中间遗忘」

这不是玄学，是有实验支撑的现象。

**结论**：模型对上下文**开头**（primacy bias）和**结尾**（recency bias）的信息利用得最好，对**中间**的信息利用明显更差，性能呈 U 形曲线。这个现象即使在使用**专门的长上下文模型**时也存在。

来源：Liu et al., *Lost in the Middle: How Language Models Use Long Contexts*（2023）—— <https://arxiv.org/abs/2307.03172>。论文结论是「改变相关信息在输入中的位置，会显著影响模型表现」，且在论文的多文档问答任务里，相关信息放在中间时的表现甚至会低于**完全不给文档**的闭卷情况。

::: tip 「上下文塞得下」不等于「上下文用得上」
模型支持的上下文长度是**容量上限**，不是**有效利用率**。把 50 个检索片段全塞进 128k 上下文，效果通常不如**只塞 5 个最相关的**。容量变大不会自动解决注意力分布的问题。
:::

### 怎么利用这一点

| 做法 | 原因 |
| --- | --- |
| **任务与规则放最前面** | 开头是注意力强的位置，约束要一直"在场" |
| **最相关的资料放最前面** | 不要按时间/字母序排，**按相关性排** |
| **真实问题放最后** | 结尾也是强位置，把要回答的东西压在最后 |
| **中间放次要资料，并且尽量少** | 中间本来就是弱区，别把关键信息藏在这里 |
| **结尾再重复一次核心要求** | 对抗长上下文衰减，成本极低 |
| **能删就删** | 减少总量是最有效的优化 |

```text
[任务 + 规则]                    ← 强位置
[最相关的 2～3 个片段]            ← 强位置
[次要片段（可以没有）]            ← 弱位置，越少越好
[再次强调：只依据上述资料回答]     ← 重复约束
[用户的问题]                     ← 强位置
```

### 长对话里的同一问题

多轮对话是长上下文问题的另一个面孔：**早期的约定会被逐渐"忘掉"**。

三种做法，按成本排序：

1. **把关键约定固化到系统提示词**，而不是依赖它出现在第 3 轮对话里；
2. **压缩历史**：把旧轮次总结成一段结构化摘要（目标、已确认的决定、未决问题）；
3. **只带最近的 N 轮**，但把摘要放在最前面。

::: warning 「上下文窗口越大越好」是个陷阱
更大的窗口意味着更长的输入、更高的成本、更慢的首 token 延迟，而且**中间部分仍然不可靠**。更常见的情况是：给足窗口反而让输出变差，因为无关内容变多了。**目标应该是「刚好够用的上下文」，而不是「尽可能多的上下文」。**
:::

## 为什么要给模型「说不知道」的出口

这是本文里投入产出比最高的一条。

**默认行为**：模型被训练成「给出回答」。当资料里没有答案时，它会从语气最像答案的地方**编造一个看起来合理的答案**。这不是故障，是它的默认策略。

**解法**：在提示词里**显式地给出「不知道」这个选项**，并说清它是什么形式。

```text
【资料不足时】
如果【资料】中没有足够信息回答问题：
- 直接回答「资料中没有相关信息」
- 说明还缺什么信息
- 不要用常识、推测或训练记忆补充
```

### 为什么必须显式写

| 不写出口 | 写了出口 |
| --- | --- |
| 模型一定给出一个答案 | 模型有了「拒答」这个合法动作 |
| 你无法区分「答对了」和「编得像」 | 拒答是一个明确的、可统计的信号 |
| 错误被伪装成自信的输出 | 失败变得可见 |

**「拒答」是 RAG 系统里最有价值的输出之一** —— 它告诉你检索没召回，或者语料本身没覆盖。如果模型从不拒答，你连自己的检索质量都测不出来。

### 几个配套做法

1. **出口要具体到措辞**。「如果不知道就说不知道」太模糊；写清「直接回答『资料中没有相关信息』」，你才能用字符串匹配去统计拒答率。
2. **提供替代路径**。好的拒答是：「资料中没有相关信息。可以尝试：换个说法查询 / 补充某类文档」。这比一句干巴巴的拒答有用。
3. **用示例固化它**。在少样本里放一个「该拒答」的例子（见上一节），比只写规则有效。
4. **区分「拒答」和「回答但注明不确定」**。有些场景是「资料里有但不完整」，这时应该要求模型**标注不确定的部分**，而不是整体拒答。

::: danger 不要用「你必须回答」施压
「无论如何都要给出答案」「不要说你不知道」这类话，会**直接关掉**上面所有努力的成果。如果你确实需要强制性输出（比如做分类），那就用结构化输出（JSON schema）约束，而不是用话术逼它编。
:::

## 一份可复用的检查清单

写提示词时逐条过：

- [ ] 系统提示词里**没有**背景资料
- [ ] 规则数量在 8 条以内，且没说反的
- [ ] 输出格式有明确的长度和结构约束
- [ ] 少样本示例**互相一致**，且格式与期望输出逐字一致
- [ ] 示例里至少有一个**边界/拒答**的例子
- [ ] 最相关的资料在**开头**，问题在**结尾**
- [ ] 没把相似度分数、内部 ID 这类对生成无用的字段塞进去
- [ ] 有明确的「资料不足时」行为定义，且措辞可被字符串匹配统计
- [ ] 温度等采样参数和任务匹配（事实型问答用低温度）

## 官方文档与我的取舍

- Lost in the Middle（论文原文）：<https://arxiv.org/abs/2307.03172>
- 各家的提示词指南都值得读，但它们**普遍不写代价**：示例越多越占上下文、规则越多越可能互相冲突、窗口越大中间越不可靠

我的取舍结论：

1. **格式与边界的约束优先于「聪明程度」的追求。** 让模型稳定做对一件小事，比让它偶尔做对一件复杂事更有价值。
2. **「说不知道」的出口是必需项。** 没有它，你连系统坏没坏都不知道。
3. **不要试图用提示词教会模型知识。** 知识靠检索（见 [RAG 最小可用实现](./RAG最小可用实现.md)），提示词只管约束和组织。
4. **上下文是稀缺资源，按重要性分配。** 两头给最重要的，中间给次要的，能删就删。
5. **本文所有经验都是方向性的**，没有在本机做过对照实验。真正适合你任务的提示词，只能靠你自己在一个固定的评测集上试出来 —— 而且要先有评测集，再改提示词。
